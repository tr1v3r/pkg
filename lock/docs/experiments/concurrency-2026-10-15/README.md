# lock 高并发实验（2026-10-15）

基线：[`6168a82`](https://github.com/tr1v3r/pkg/commit/6168a828463241acc28db1e500fcc8676dea5016)。本次只增加独立实验与报告，未修改生产实现，也不把压测加入默认单元测试。后续并行开发的 PostgreSQL 驱动不在实验范围内。

## 结论

- 三轮性能矩阵共 **39 组**，另有 **5 组 1000 路 race 负载**，全部通过。未观测到重复放行、临界区重叠、租约异常失效、owner 不一致、请求错误或连接池超时。
- 总连接上限 64 时，1000 路多 key `TryRun` 的吞吐中位数约 **27,451 次/秒**，每组 P99 的中位数 **304.29ms**；多 key 租约获取→显式续期→释放约 **9,872 轮/秒**，P99 **316.94ms**。前者一次 SET，后者一轮含三次 Driver 请求，两者不能直接当成同一操作比较。
- 同一 key 上，1000 个调用方各完成一次 `Lock`→临界区→`Release`，吞吐约 **153 轮/秒**，P99 **6.47 秒**。获取请求次数中位数 **193,617**，约为成功次数的 **194 倍**。这是实测的竞争与重试放大；P99 包含等待、名义 100µs 临界区、调度和释放，并非一次 Redis 请求耗时。
- **5000 个自动续期租约**使用 3 秒 TTL，在全部获取完成后再观察 7 秒。三轮均无本地失效、无未续期及远端 owner 不一致。64 连接时续期 Driver 请求 P99 中位数 **380.09ms**；每轮约 35,000 次续期。
- 5000 租约的采样 goroutine 峰值中位数 **10,002**，符合每个自动续期租约两个 worker 的实现；客户端 Go HeapAlloc 采样峰值约 **58.42MB**，包含客户端、统计器及临时分配，不是库的精确保留内存。每个案例释放租约、关闭客户端并等待 100ms 后，goroutine 数均从基线 1 回到 1。
- 此环境把连接上限从 64 增至 256，没有改善 1000 路多 key 的吞吐中位数，且增加客户端内存。热点 key 的固定 10ms 重试、每租约 worker 的规模成本值得后续单独比较；本次不据此直接修改实现。

## 环境与统计口径

- 客户端：Apple M3 Pro，12 个逻辑 CPU，36GiB 内存；Go 1.25.7，darwin/arm64，`GOMAXPROCS=12`。并发数是显式创建的工作 goroutine 数，不依赖 `RunParallel`。
- Redis：真实 Redis **7.4.11**，独立 OrbStack Docker 容器，2 CPU／512MiB 限额，关闭 AOF 与快照持久化；macOS 经本机发布端口连接 Linux 容器。镜像摘要见 [environment.json](environment.json)。现有其他容器未修改。
- 4 个独立 go-redis 客户端共享 key 命名空间，总连接上限为 64 或 256。**同时配置 `PoolSize` 和 `MaxActiveConns`**，不是只设置基础池大小。预热池后开始计时。
- `ContextTimeoutEnabled=true`、`MaxRetries=-1`，每次 Driver 操作超时 2 秒，池等待超时 2 秒；`Lock` 的重试间隔 10ms、单次等待上限 20 秒。
- 正常构建测性能，race 构建独立测正确性，两阶段不并发。三轮按固定种子调整场景顺序，场景间串行。
- 下表为**三次运行的吞吐和各次 P99 的中位数**；范围是三次 P99 的最小／最大值，不是把所有样本合并后的 P99。波动较大，不能视作稳定生产容量或尾延迟上界。
- 顶层调用和 Driver 请求分别采样；Driver 请求耗时包含池等待、客户端、网络与 Redis，不能直接解释为服务端耗时。资源每 20ms 采样一次；统计、采样也有开销，短时峰值可能漏采。
- 闭环固定请求数，工作 goroutine 完成上次调用后才发起下次；包含同步突发与池排队，**没有模拟开放到达率、跨机器网络、Redis failover/Cluster 或长时间 soak**。没有外推无 fencing 情况下的严格互斥保证。

## 场景

| 标识 | 负载与正确性断言 |
| --- | --- |
| gate-hot | N 个 goroutine，每人依次尝试 3 个共享窗口 key；60 秒 TTL，共 N×3 次 TryRun，只允许总计 3 次回调。测的是尝试吞吐，绝大多数为 busy，并非业务执行吞吐。 |
| gate-many | N 个 goroutine，每人 30 次 TryRun，每次唯一 key；60 秒 TTL；全部应执行，共 N×30 次。 |
| lease-hot | N 个 goroutine 同抢一个 key，每人一次 Lock；TTL 5 秒，临界区名义 sleep 100µs 后释放；原子计数器检查临界区不重叠，检查持有期间未失效。 |
| lease-many | N 个 goroutine，每人独立 key，连续 10 轮 TryLock→Renew→Release；TTL 5 秒，全部应成功。 |
| auto | 同步启动 N 个获取请求，独立 key，TTL 3 秒、自动续期；全部获取完成后继续观察 7 秒，逐个检查本地状态、deadline 已推进、Redis owner 仍一致，然后并发释放。 |

## Race 与清理

单独用 `-race` 构建运行 1000 路 gate-hot、gate-many、lease-hot、lease-many、auto 各一组，退出码均为 0，stderr 均为空。性能数据未采用这些运行。race 通过只说明这些执行未发现数据竞争。

每个案例只扫描／删除自己的随机命名空间，未使用 FLUSHDB。最终隔离 Redis 的 `DBSIZE=0`，本次容器已删除；生产源码工作区及并行开发内容保持原状。

```sh
shasum -a 256 -c SHA256SUMS

sh run-reproduce.sh
```

复现脚本自动创建专用容器、使用本机随机端口，并在退出时清理。需要 Python3、Docker、Go；race 构建需要对应平台的 C 工具链。若只跑一个场景，在构建后使用 `./lockstress -addr <地址> -scenario lease-many -workers 1000 -iterations 10 -pool 64 -clients 4 -procs 12`。
